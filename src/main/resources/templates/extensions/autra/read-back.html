What a merchant's own app can ask autra about a payment

Autra publishes two read-only addresses on its acquiring surface. One answers a single payment and the timeline of everything that has happened to it, GET /v1/acquiring/payments/{paymentId}. The other lists the payments of one establishment in a window of dates, newest first, GET /v1/acquiring/payments. Neither calls the acquirer and neither changes anything, so reading a payment here as many times as you like leaves the test run exactly as it was.

This screen shows the state those two routes answer from, for every card payment of this test run at once: it reads what this simulator stored rather than asking autra's own addresses, so there is nothing to fill in here. To ask those two addresses themselves, with the query a merchant's own app sends and the refusal autra answers a bad one with, open the Look a payment up screen: it performs the two reads autra declares and prints what each one answered, under the names autra answered them under. The identifiers below are the ones autra draws, and a merchant's own app sends them back verbatim.

Pre-authorizations still open

This is what autra publishes the listing address for: finding the reservations a merchant is still holding, so a void can release the cardholder's limit instead of waiting for a daily routine. Autra's own example of that query is ?status=ACCEPTED&type=PREAUTH, and this simulator answers ACCEPTED to a pre-authorization, so that query is the one that selects these here too. A sale answers the same word, which is why the query names type as well.

This test run is holding no open pre-authorization. A reservation appears here from the moment autra takes it until a capture or a void closes it.
