Why the two kinds of key are never in one list

A key whose repeat returns the original response and a key whose repeat is refused are opposite behaviours, and this screen never puts them in one list. The simulator owns what each role means; the provider owns which of its own fields fills the role and what it compares a repeat against. This screen shows exactly what returns and offers exactly what that control API can do.

Why nothing on this screen can be rewritten

This screen changes nothing. A response a true idempotent replay has already established cannot be rewritten here, because the control API this screen stands on offers no way to rewrite one: a tester steers the next answer by writing a scenario for a request that has not been made yet.
