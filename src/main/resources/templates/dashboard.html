Why this screen sums every provider, and what registers a test run

This is the one screen that is not about a single provider. Every count below is a sum over every provider this simulator serves, taken in the simulator's own words, and the per-provider screens are a click away in each row.

A run is registered when a configuration call, a pinned clock or a scenario rule names it. A run that nothing has registered is still reachable by typing its name, and the run a request that names none belongs to is always listed. Naming a new run here carries you to the account form rather than registering the name on its own, so a run comes into existence because a configuration named it and an abandoned form leaves nothing behind.

A run is touched by everything the audit trail records of it: every call a client made to a provider, and every configuration, scenario and screen action a tester took. A run is therefore touched from the configuration that registered it, and the count above is the trail's rows and not the provider API traffic the panel below counts. The order is the order the trail recorded those rows in, which stays true however a run's clock is pinned, and the stamp is the newest row's time on that run's own clock, so a run pinned to last year reads last year.

Forgetting a run empties it in every provider, drops its registration and records what it did against the run you are reading rather than the one it emptied, so the forgotten run leaves no row behind. It is refused for the run being read and for the run a request that names none belongs to, and neither offers the button at all.

How many exchanges this reads, and why both directions are here

The newest calls a client made to each provider are read, the newest callback attempts that provider made to a merchant are read beside them, and the newest of them all are shown, so an older exchange is reached from Audit and not from here. Every row links to the one exchange it is, by the audit id that exchange was recorded under, so a row that touched no object is opened by that link too. Callback attempts the simulator made to a merchant are listed beside the calls a client made to a provider, because hiding one direction would hide the half of a flow that failed. The panel below this one lists the callbacks a merchant has already refused; an attempt still waiting on another try is here and not there.
