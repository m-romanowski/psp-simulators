How an alias is matched, what outranks it, and what releasing one is for

A request arriving on the host and path of an alias is served as the route beside it and belongs to this test run, and the audit trail records the URL the application called rather than the route that answered it. The alias is matched on the host and the whole path exactly, with no prefix and no wildcard, and the host is read from X-Forwarded-Host when a proxy sends one and from Host otherwise. The test-run header outranks an alias; an alias outranks the credentials a request carries. Binding a URL an alias of another test run already holds is refused rather than taken from it, and binding one this run already holds replaces the route it pointed at. Releasing a URL is the only way to free it for another test run: a configuration that leaves an alias out leaves it bound, and reset never touches it.

Whose clock this is, how to release it, and what advancing it expires

The clock belongs to the test run and not to a provider, so pinning it here moves time for every provider of . Leave the field empty and submit to release the run back to the host clock. Nothing scheduled falls due on a pinned clock until the clock is moved.

Advancing takes a number and a unit and adds that span to the instant this run is pinned to, so two advances of an hour each leave the run two hours ahead of where it started. A control call writes the same span as an ISO-8601 duration. Advancing is the only control this simulator offers for making something fall due or run out: a hosted session, a hold, a token, a scheduled callback and a retry all carry a deadline recorded when they were created and compared against this clock, so moving the clock past a deadline expires that one thing and nothing else. A run that reads the host clock cannot be advanced, because a duration added to a clock that is already moving names no instant; pin it first.

Why routing by header is not authentication

This header routes; it does not authenticate, and it is listed apart from the permissive modes below for that reason. A request that names a test run is still checked against the credentials configured for that run, and a header naming a run those credentials do not belong to is refused like any other credential failure. A header naming a test run that does not exist is refused rather than falling through to the credentials.
